1 · Issuer identity

did:key

The public identifier is derived directly from an Ed25519 Multikey. A verifier can resolve the verification material without trusting our webpage.

2 · Proof format

DataIntegrityProof

The signing path uses eddsa-rdfc-2022, matching the cryptosuite used in current MIT/DCC Open Badges examples.

3 · Institution trust

Still deliberately separate

This proves technical interoperability for a demo issuer. It does not make the demo issuer Implement or University of Basel.

External verifier handoff

Generate the credential locally, verify it with the repo's independent round-trip check, then take the generated JSON outside this application. VerifierPlus is the DCC reference surface we use for the manual compatibility check.

01 · GenerateRun npm install and npm run dcc:roundtrip.
02 · Take the artefactOpen obv3/dcc-signed-credential.json. The private key remains in the ignored .keys/ directory.
03 · Verify elsewherePaste/import the credential into VerifierPlus. This tests the object outside our own verifier and UI.

What this does — and does not — prove.

It proves: our product data can become an Open Badges 3.0 credential with a DCC-shaped issuer identifier and Data Integrity proof that an independent verifier can process.

It does not prove: that Implement or University of Basel authorized the credential. For that, the signing identity and keys must be institution-controlled — preferably a production did:web or an institution-managed equivalent, with governance and revocation.
